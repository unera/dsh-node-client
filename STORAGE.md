# Хранилище клиента: правила

Три файла в `~/.dshnc` (или в `$DSHNC_HOME`), и у каждого своя природа. Смешивать
их нельзя: раньше всё лежало в одном `config.json`, и демон, сохраняя курсор
после каждой команды, затирал правки, сделанные рядом из CLI.

| файл | что внутри | кто пишет |
|---|---|---|
| `config.json` | только человеческие настройки: `id`, `name`, `aliases`, `workdir` | CLI и демон (через хранилище) |
| `credentials.yaml` | токены узлов, режим `0600` | тот, кто подключает узел |
| `state.sqlite` | рантайм: `epoch`, `boot`, `node`, `alias`, `api_ids` | только демон |

## Схема `state.sqlite` меняется только цепочкой миграций

1. **Миграции исполняются при открытии хранилища** — `openStore()` в
   `lib/store.mjs` прогоняет цепочку до того, как вернуть объект. Никаких
   отдельных команд «обнови базу»: открыл — значит привёл в порядок.
2. **Учёт исполненного — в самой БД**, в таблице `migrations (id TEXT PRIMARY KEY,
   applied_at INTEGER)`. Шаг с уже записанным `id` повторно не применяется,
   даже если файл открывали старым клиентом и вернули новый.
3. **`id` шага постоянный**, вида `0002_split_config`. Порядок в массиве
   `migrations` — это порядок применения. Удалять и переименовывать шаги нельзя,
   только добавлять новые в конец.
4. **Рантайм восстановим**, поэтому шаг вправе пересоздать таблицу. Потеря
   курсора стоит одного круга: клиент объявится заново, а сервер сам скажет
   сбросить курсор при смене поколения (`epoch`). Героически спасать данные
   рантайма не нужно.
5. **`meta.schema_version`** хранит `id` последнего применённого шага — для
   людей и диагностики, а не для логики: логика смотрит в `migrations`.

## `credentials.yaml` — список, а не карта

Формат:

```yaml
servers:
  - url: https://dsh.uvw.ru/dsh-nodes
    token: <base64url>
```

Ключ-урл в YAML удобен машине и неудобен человеку: редактор подсвечивает двоеточия
в адресе как ошибку, а глазам тяжело. Поэтому список объектов — по одному серверу
на запись.

Старый формат (карта `url: token` верхним уровнем) **читается** — обновление
клиента не должно стирать токены. Пишется всегда новый.

## `config.json` и `credentials.yaml` тоже версионируются

Поле `version` добавляется при первом же несовместимом изменении формата:
преобразование только «вперёд», данные человека (настройки, токены) не теряются.
Для `state.sqlite` это не нужно — там цепочка миграций.

## Песочница и права

Клиент исполняет команду в `bwrap`, если запрошенный режим не `full`:

| режим | что можно | сеть |
|---|---|---|
| `ro` | только чтение всего хоста | отрезана (`--unshare-net`) |
| `rw` | запись в каталог узла (`workdir`) и в `/tmp` | отрезана |
| `full` | всё, без песочницы | есть |

Профиль повторяет DSH (`--ro-bind / /`, `--unshare-pid`, `--proc /proc`,
`--die-with-parent`), потому что их пакет тянет cordis и платформенные ветки,
а нам нужны 40 строк с предсказуемым поведением. Атрибуция: таблицы сигнатур
отказа и лестница режимов взяты из `@deepseek-ai/dsh-sandbox-local` (MIT).

Важное следствие `bwrap`: `no_new_privs` выставляется автоматически, поэтому
`sudo` и setuid-бинарники внутри не работают — повысить права из песочницы
нельзя.

**Что песочница НЕ делает:** при `ro` и `rw` весь хост остаётся читаемым. Это
осознанное решение: `~/.ssh`, токены, домашний каталог видны команде. Если узел
отдаётся другому человеку, правильный ответ — отдельный пользователь ОС, а не
попытка спрятать файлы в песочнице. Пересмотрим, если появится сценарий, где это
недостаточно.

## Политика доступа: потолок и вопросы

Владелец узла задаёт правила один раз: узел служит одному серверу, поэтому
правила плоские, рядом с адресом.

```yaml
server: https://dsh.uvw.ru/dsh-nodes
max: full        # потолок прав
base: rw         # стартовый режим
approver: local  # кто отвечает на «разрешить шире»
```

`max` — потолок: эффективный режим считается как более узкий из запрошенного
сервером и потолка. `approver: none` означает, что отказ песочницы не
превращается в вопрос: отказ окончательный, и в тексте прямо сказано, что
апрувы на узле запрещены.

Задать из CLI:

```sh
dshnc config max=full approver=none
dshnc config                      # что настроено
```

Второй узел на этой машине — второй конфиг: `dshnc -c /etc/dshnc/backup.yaml daemon`.
Токены при этом общие (`credentials.yaml`, ключ — адрес сервера).

## Каталоги сессий и плагин `session`

Встроенный плагин `session` (не внешний инструмент, а реконфиг сессии):

| метод | что делает |
|---|---|
| `chdir { path }` | переключает рабочий каталог сессии; каталог **должен существовать** |
| `mkdir { path, mode }` | создаёт каталог (по умолчанию 0755) внутри разрешённых корней |
| `cwd {}` | показывает текущий каталог |

`chdir` намеренно не создаёт ничего: неявное создание каталогов — это сюрприз,
о котором потом не помнишь. Создание — отдельный метод.

Выбор хранится в `state.sqlite` (таблица `session_workdir`), поэтому переживает
рестарт демона. Путь проверяется по `roots` из настроек узла; по умолчанию это
сам `workdir`. Вне `roots` — `workdir_denied`.
